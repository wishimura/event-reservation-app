# 全体レビュー（決済・在庫・当日運用が止まらないか）

2026-09-29 実施。観点は「お金が正しく動くか」「在庫が正しく動くか」
「混んだときに止まらないか」の3つ。セキュリティは別。

本番と同じ構成（Next.js + Postgres）をローカルに立て、**東京〜シンガポール間の
往復遅延（片道35ms）を挟んだうえで**実測した。本番は Vercel が東京、Neon が
シンガポールなので、DBへの1往復ごとに約70msかかる。この往復の回数が、混雑時に
効いてくる。

---

## 1. いちばん怖かったところ（直した）

### 決済は通ったのに「失敗しました」と出る経路があった

カードを切ったあと、その結果をDBに書き込む処理が同じ `try` の中にあり、
**書き込みだけが失敗した場合も「決済失敗」として扱われていた**。
そのとき起きること:

1. お客様のカードからは引き落とし済み
2. 在庫は返却される
3. 画面には「カードの決済に失敗しました」
4. お客様はもう一度カードを切る → **二重請求**

決済が成功した時点で線を引き、それ以降は何が起きても
「予約は成立している」として扱うように変更した。書き込みは3回まで再試行し、
それでもダメなら注文番号と Square の決済IDをログに残して、お客様には
予約完了画面を出す（お店側は後から突き合わせられる）。

### 通信が切れたあとの再送で二重請求になる

スマホの電波が切れると、決済が通ったかどうかブラウザからは分からない。
「エラーが発生しました。もう一度お試しください」と出るので、お客様は
もう一度押す。サーバーから見ると別の注文なので、もう一度課金される。

ブラウザが注文ごとに固有のIDを付けるようにした（`client_request_id`）。
同じIDの注文が2回届いたら、2件目は新しい注文を作らず、1件目の結果を返す。
在庫も二重には引き当てない。通信断のときはブラウザが自動で1回だけ再送する
ので、多くの場合お客様は失敗に気づかない。

実測（同じIDで同時に5発）: 作られた注文 1件、引当 1件分、残り4つには
同じ注文番号が返る。

### Vercel の関数タイムアウトが未設定だった

`maxDuration` を指定していなかったため、既定値（プランによっては**10秒**）で
打ち切られる可能性があった。注文1件は DB に何度も往復したうえで Square を
呼ぶので、混雑時に10秒は超えうる。**打ち切られた瞬間が課金の最中だと、
お金だけ動いて予約が残らない。**

注文APIに `maxDuration = 60` を明示した。あわせて Square の呼び出しにも
12秒のタイムアウトを設定（再試行2回まで。冪等キーがあるので二重課金にならない）。

## 2. 混雑したときに止まらないか（直した）

### 計測してわかったこと

注文1件あたり、DBと**12回**往復していた。しかもそのうち**8回**は、
その商品の在庫行をロックしたまま。次のお客様はその間ずっと待つ。

70ms × 8 = 約560ms。つまり**同じ商品なら毎秒2件弱しか捌けない**。

### 改善内容

- 在庫を押さえる処理を、注文を書き終えた**あと**に移動（ロックを握る時間を短く）
- 商品ごとに分かれていた在庫更新を**1文にまとめた**
- 受取日の状態（受付中／残りわずか／受付終了）の再計算を、読み取り＋書き込みの
  2往復から**1文に**
- 受取日とイベントの取得を1回の JOIN に
- トップページの取得も1回の JOIN に
- DB接続プールを 5 → 10（注文が接続を握っている間、閲覧が待たされるのを緩和）

結果、**往復12回 → 8回、ロック中は8回 → 3回**。

### 告知直後を想定した実測（注文100件＋閲覧200件を同時にぶつける）

| | 改善前 | 改善後 |
| --- | --- | --- |
| 注文の中央値 | 26.6秒 | **10.4秒** |
| 注文の最大 | 48.2秒 | **17.7秒** |
| 閲覧の中央値 | **48.7秒** | **1.7秒** |
| 閲覧の p95 | 50.0秒 | 2.4秒 |
| 失敗 | 0件 | 0件 |

改善前は、**注文していない・ただ見ているだけの人まで50秒待たされていた**。
これが「サイトが止まってしまう」状態そのもの。改善後は1.7秒で返る。

しかも改善前の数字は、Vercel の既定タイムアウトが10秒だった場合、
ほとんどが打ち切られて 504 になっていた。

## 3. 在庫が狂わないか（問題なし・再確認した）

- **在庫がないのに決済できるか** → できない。在庫の引き当ては
  `予約数 + 注文数 <= 受付上限` という条件付きの UPDATE で、Postgres が
  ロック解放後に条件を再評価する。同時に来ても上限を超えない。
  さらにDBの CHECK 制約が最後の砦として同じ条件を持っている。
  - 実測: 在庫20個に同時40件 → **成功20件、残り20件は「残り0個」と案内**。
  - 実測: 最後の1個に同時6件 → **成功1件**。
- **決済が失敗したら在庫は戻るか** → 戻る。
- **キャンセルで在庫は戻るか** → 戻る。売り切れだった日も受付中に戻る。
- **店頭販売の登録でも在庫は減るか** → 減る。オンライン注文と同じ処理を共有。
- **管理画面から受付上限を下げたとき** → すでに予約が入っている数より下には
  下げられず、商品名を挙げて断る。

### 追加で直したところ

- 在庫保存（管理画面）と注文とで、行をロックする順番が違っていた。
  最悪の場合デッドロックになり、**お客様側の注文が巻き添えで落ちる**。
  どちらも同じ順に揃え、保存時は `FOR UPDATE` で読むようにした。
- **決済が途中で止まった注文が在庫を握ったまま**になるケースがある
  （関数が落ちた、在庫返却も失敗した、など）。誰も気づけないまま、その日の
  枠だけが減る。30分以上「未決済のまま」の注文を**ダッシュボードに赤く出す**
  ようにした。Square 側に決済が無ければ注文一覧でキャンセルすれば枠が戻る。

## 4. 当日の運用が重くならないか（直した）

注文が1000件たまった状態で管理画面を計測した（このイベントの上限は
13日 × 141個 ≒ 1800個なので、注文は1000件弱が上限の目安）。

| 画面 | 改善前 | 改善後 |
| --- | --- | --- |
| ダッシュボード | 944 KB | **5.9 KB** |
| 注文一覧 | 1.96 MB | 1.45 MB＋100件ずつ表示 |
| 製造計画 | 50 KB | 50 KB |
| 受取管理（当日） | 1 KB | 1 KB |

- ダッシュボードは合計を出すためだけに全注文を取り寄せていた。合計はDB側で
  計算するようにした（数字は同じ）。
- 注文一覧は、画面で使っていない商品マスタを注文明細ごとに付けて送っていた。
  やめた。表示も100件ずつにして、スマホで1000行を一度に描かないようにした。
  **検索・絞り込みは全件に対して効く**（表示だけを止めている）。
- 当日いちばん使う受取管理は元から1KB。ここは速い。

## 5. その他に見つけて直したこと

- 読み込みが終わる前に「注文を確定する」を押すと、**何も起きず無反応**だった
  （エラーも出ない）。ボタンを読み込み完了まで押せなくし、押された場合も
  理由を表示するようにした。ブラウザテストが実際に踏んだ。

## 6. 直していない・お店側で確認が必要なこと

### 至急

1. **`SQUARE_ENVIRONMENT` が `production` になっているか**
   サンドボックスのままだと、本物のカードは必ず失敗する。
   確認方法: ブラウザで
   `https://gegege-event-reservation-app.vercel.app/api/payments/config`
   を開き、`applicationId` が `sq0idp-` で始まっていれば本番、
   `sandbox-` で始まっていればテスト環境。
2. **`SHOW_LOGIN_HINT` を Vercel の環境変数から削除**
   残っていると、公開されているログイン画面に管理パスワードが表示される。
3. **DBのパスワードを変更**（チャットに貼られたため）

### 仕様として決めておくこと

- **1人が1日の在庫を全部買えてしまう**。20個のカレーを1人で全部予約できる。
  「1人◯個まで」の上限を入れるかどうかは、お店の判断。入れるなら実装は簡単。
- **Square が落ちたら決済できない**。これは避けられないが、非常口はある:
  Vercel の環境変数から `SQUARE_ACCESS_TOKEN` を消して再デプロイすると、
  **カード決済なしの「現地払い」モードに切り替わり、予約は受け続けられる**。
  お金は当日レジで受け取る運用になる。
- **Neon（DB）が落ちたらサイトは止まる**。こちらは代替手段がない。

### 残っている小さいもの

- `event_dates.reservation_open` 列は誰も読んでいない（消してよい）
- `warning_threshold`（「残りわずか」と出す閾値、既定3個）を変える画面がない
- 商品が1つでも残り3個以下になると、その日全体が「残りわずか」表示になる

## 付録: このレビューの再現手順

```bash
# 1. ローカルに Postgres を立てて、本番同等のデータを入れる
initdb -D /var/tmp/pg -A trust -U postgres
pg_ctl -D /var/tmp/pg -o '-p 5455' start
createdb -h localhost -p 5455 -U postgres app
for f in drizzle/*.sql; do psql -h localhost -p 5455 -U postgres -d app -f $f; done
psql -h localhost -p 5455 -U postgres -d app -f docs/production-data-2026-11.sql

# 2. 遅延プロキシを挟む（本番の東京〜シンガポールを模す）
#    片道35ms 遅らせて 5456 → 5455 に中継するだけの TCP プロキシ

# 3. ドライバを一時的に node-postgres に差し替えて起動（コミットしないこと）
#    詳細は tests/README.md

# 4. テスト
npm test                    # 単体 25件
npm run test:integration    # 結合 43件
npx tsx tests/scenario.e2e.ts   # ブラウザ 11シナリオ
```
