# テストシナリオ一覧

このシステムで「何を確かめているか」を全部書き出したもの。
自動テストになっているものは ✅、手で確かめるものは 👤、確かめられない理由があるものは ⚠️。

E2E が何を保証しているかの目次は `docs/シナリオテスト仕様書.md` にあります
（本書は全量の棚卸し、あちらは E2E の約束です）。

| 層 | ファイル | 件数 | 準備 |
| --- | --- | --- | --- |
| 単体 | `tests/unit.test.ts` | 50 | 不要 |
| 結合 | `tests/api.test.ts` / `admin.test.ts` / `deep.test.ts` | 68 | 使い捨てDB＋起動中のサーバー |
| 結合（決済） | `tests/payment.test.ts` | 5 | 上記＋Square の認証情報を入れたサーバー |
| E2E | `tests/e2e/*.e2e.ts` | 33 × 2構成 = 66 | 専用DB（`E2E_DATABASE_URL`） |

```bash
npm run check             # lint → 型 → 単体50件 → 仕様書とE2Eの対応
npm run test:integration  # 結合 68件
npm run test:payment      # 決済 5件（BASE_URL を決済有効サーバーに向ける）
npm run test:e2e          # ブラウザ 33件 × PC幅・スマホ幅
```

E2E の列に書いてある `S-NN` は `docs/シナリオテスト仕様書.md` の節番号です。
`npx playwright test -g "S-05"` で、その節だけ流せます。

> ※ 1.17 は本番でお客様からご指摘がありました。完了画面には
> 「クレジットカード（お支払い済み）」と出るのに、届くメールには
> 「お支払いはご来店の際に店頭でお願いいたします」と書いてあり、決済できたのか
> 分からない状態になっていました。メールを組み立てるところに支払い方法を
> 渡しておらず、常に現地払いの文面になっていたためです。

> ⚠️ **1.13 について**: この経路を自動で確かめるには「Square の決済が成功し、かつ
> その直後のDB書き込みだけが失敗する」状況を作る必要があり、本物の決済を伴わずには
> 再現できません。コードの構造としては、決済成功の時点で `try` を抜け、以降は
> 取り消し処理を一切呼ばない形にしてあります（`src/app/api/orders/route.ts` の
> `recordPayment`）。書き込みは3回まで再試行し、それでも失敗したら注文番号と
> Square の決済IDをログに残したうえで、お客様には予約完了を返します。
> 加えて、そうして取り残された注文は管理画面のダッシュボードに警告として出ます（4.9）。

> **E2E では決済を通していません。** Square の鍵を渡していないので、アプリは
> 現地払いのまま動きます。画面の流れはそれで確かめられますが、
> **カード決済が通ること自体は本番で人が1件通すしかありません**（12.1）。
