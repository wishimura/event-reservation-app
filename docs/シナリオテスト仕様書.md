# シナリオテスト仕様書

**この文書は「E2E が何を保証しているか」の目次です。**

- **手順は書きません。** どのボタンをどの順で押すかはテストコードが正です
- **業務ルールも書きません。** なぜそうなるかは `docs/test-scenarios.md` と
  `docs/reliability-review.md` が正です
- ここに書くのは**保証すること**だけ。壊れたら困る性質を1行ずつ並べます

書く内容を絞っているのは、**自動化が進むほどこの文書が縮む**ようにするためです。
手順表を残すと、画面を触るたびに文書と実装がずれ、やがて誰も直さなくなります。
手順の台本が要るときは、テスト用のチェックリストを別に作ってください（この文書ではありません）。

仕様が変わったら **① 実装 → ② 本書の「保証すること」 → ③ テストコード** の順で直します。

## 前提

- 実行: `npm run test:e2e`（PC幅とスマホ幅の2構成で、全シナリオを両方回します）
- データベース: **専用のものが要ります**。`E2E_DATABASE_URL` に指定してください。
  テーブルを空にするので、`DATABASE_URL` と同じだと安全ガードが止めます
- 前提データ: 各テストが `beforeEach` で作り直します（`tests/e2e/_helpers/fixtures.ts`）。
  受取日は今日から数えるので、日付が過ぎて使えなくなることはありません
- 決済: **E2E では Square の鍵を渡しません。** 鍵が無ければアプリは現地払いのまま
  動くので、画面の流れはそのまま確かめられます。カード決済そのものは
  `tests/payment.test.ts` で見ます（下の「保証していないこと」も読んでください）

## 本書とテストコードの対応

**`test.describe` はシナリオ番号から始めます。** 落ちたテストの名前を見れば、
本書のどのシナリオかがすぐ分かります。番号で絞って実行することもできます。

```bash
npx playwright test -g "S-05"   # 名寄せのシナリオだけ
npm run check:scenarios         # 本書とテストの対応がずれていないか検査
```

`check:scenarios` は本書の `S-NN` と `test.describe("S-NN …")` を突き合わせ、
**片方にしか無い番号があれば落ちます**。シナリオを足すときは本書とテストの両方に、
消すときも両方から。

## S-01 お客様の予約

**テスト**: `tests/e2e/customer.e2e.ts`

**保証すること**

- トップ → 受取日 → 商品 → 確認 → 完了まで、途中で止まらずに通る
- 完了画面に注文番号（`ORD-……`）が出る
- **受取時間の枠を選ばせる画面がどこにも残っていない**（廃止した仕様）
- 受付を止めた受取日は**押せない**。画面を飛ばして直接送っても断られる
- 存在しない受取日・UUID ですらない文字列の URL でも、エラー画面にならない
- 売り切れの商品は売り切れと分かり、数量の欄そのものが出ない
- スマホ幅で横にはみ出さない

## S-02 お召し上がり方法

**テスト**: `tests/e2e/dining-style.e2e.ts`

**保証すること**

- 店内・持ち帰りの**どちらも最初から選ばれてはいない**
- 選ばないまま送ると止まり、**区分の無い注文が作られない**
  （区分が無いと、納める消費税の根拠が失われる）
- 店内なら「来店日」「イートイン」、持ち帰りなら「受取日」「テイクアウト」と呼ぶ
- **売値は区分で1円も変わらない。** 変わるのはお店が納める消費税だけ

## S-03 在庫

**テスト**: `tests/e2e/inventory.e2e.ts`

**保証すること**

- 残りの数を超えて入れようとすると、**理由と残数が同じ画面に出る**
  （上限のボタンは無効にしない。押したときに理由を返すため）
- 1つ売れたら、次のお客様には残りが減って見える
- 管理画面でキャンセルすると、**お客様側の残りが戻る**
- 売切にすると、お客様の画面でも売切になる
- 受付上限を予約数より下げようとすると、**どの商品で通らなかったかが分かる**
- **その日だけ並ばない商品があれば画面が知らせ、その場で直せる**
  （行が無い商品はその日には存在しない扱いになる。戻しても受付枠は0）

## S-04 管理画面

**テスト**: `tests/e2e/admin.e2e.ts`

**保証すること**

- すべての画面が、エラーでも「読み込みに失敗しました」でもなく中身を出す
- `NaN` や `undefined` が画面に出ない
- スマホ幅で横にはみ出さない（カウンターでは手元の端末を使う）
- 予約が注文一覧に、提供区分つきで出る
- 予約した数が製造計画に出る
- CSV に**納める消費税の根拠**が入っている
- **決済までたどり着けなかった失敗が、決済ログに残って管理画面から読める**
  （注文もキャンセルも残らない失敗なので、これが無いと後から何も分からない）
  （提供区分 / 税率 / 税抜額 / 消費税額 / 当日変更 / Square決済ID）

## S-05 受取管理と名寄せ

**テスト**: `tests/e2e/pickup.e2e.ts`

**保証すること**

- 同じ連絡先の予約は1枚にまとまり、**まとめた理由がその場に書いてある**
  （黙ってまとめるのがいちばん危ない）
- まとまっていても、注文は1件ずつ見える
- **同姓同名でも連絡先が違えば別の方として扱い**、両方のカードに取り違えを
  防ぐ注意書きが出る
- 名前でもメールでも注文番号でも、検索すればまとまりごと出てくる
- カウンターで区分を切り替えられ、**金額は1円も変わらない**（決済は終わっている）
- 切り替えは何度でも行き来でき、画面を読み直しても残る
- 1件ずつでも、残りをまとめてでも渡せる。押し間違いは戻せる
- **既定では畳んであり、押すと開く**（当日は20件ほど並ぶ）。畳んだままでも
  お名前・連絡先・残り件数と**同姓同名の警告**は見えている
- 検索しているあいだは開いたまま（番号で引いてもう一度押させない）

## S-06 店頭販売

**テスト**: `tests/e2e/walk-in.e2e.ts`

**保証すること**

- 登録すると受付枠が減り、店頭として記録され、提供区分も残る
- 受付枠より多くは登録できない

## S-07 管理画面のログイン

**テスト**: `tests/e2e/auth.e2e.ts`

**保証すること**

- ログインしていないと、**どの画面もログイン画面に戻される**
  （管理画面にはお客様全員の氏名・メール・電話が入っている）
- 間違ったパスワードでは入れない
- ログアウト後は、ブラウザの戻るボタンでも入れない
- ログイン画面にパスワードが書かれていない（`SHOW_LOGIN_HINT` の消し忘れ）

## S-08 特定商取引法に基づく表記

**テスト**: `tests/e2e/legal.e2e.ts`

**保証すること**

- 予約の画面からたどり着ける
- 載せなければならない項目が埋まっていて、書きかけの印が残っていない

## S-09 カード払いの画面

**テスト**: `tests/e2e/card-form.e2e.ts`

**保証すること**

- カード欄の**置き場所が必ず画面に用意される**
  （置き場所が無いうちに Square を差し込もうとして、本番で2回壊れた）
- 立ち上げに失敗したら、**そのことが記録に残る**（お客様の端末で起きる失敗は
  サーバーに何も残らないため）

> E2E のサーバーには Square の鍵を渡していないので、`/api/payments/config` の
> 返事だけを差し替えてこの画面を作っています。カード入力欄そのものが描けるか、
> 決済が通るかは、ここでは分かりません。

## 保証していないこと（人が確かめる）

E2E が緑でも、ここは確かめられていません。**緑を見て「大丈夫」と思わないでください。**

- **カード入力欄そのもの。** Square の鍵を渡していないので、カード欄も
  Apple Pay / Google Pay のボタンも、どのテストでも描かれません。2件目の注文で
  カード欄が出なくなる不具合（画面を離れるときに片付けていなかった）は、ここが
  空白だったために自動では捕まえられませんでした
- **カード決済が本当に通ること。** E2E では Square の鍵を渡していないので、
  アプリは現地払いのまま動きます。決済の失敗側の後始末は
  `tests/payment.test.ts` で見ていますが、**成功経路は本番で人が1件通します**
- **確認メールが届くこと。** E2E では送信しません。文面の組み立ては
  `tests/unit.test.ts`、送信の分岐は `tests/deep.test.ts` までです
- **本番の混雑。** 200人が同時に予約したときの挙動は
  `docs/reliability-review.md` の実測が根拠です
- **日本語入力（IME）の挙動**、実機の操作感 — ブラウザ自動化からは見えません

## テストの置き場所

何をどこで確かめるかを間違えると、遅くて壊れやすいテストが溜まります。

| 対象 | 置き場所 | 理由 |
|---|---|---|
| 計算（税・金額）、文字列、日付、名寄せの判定 | `tests/unit.test.ts` | 速くて壊れにくく、境界値を大量に書ける |
| API の応答、権限、おかしな入力 | `tests/api.test.ts` / `admin.test.ts` / `deep.test.ts` | HTTP を通らないと確かめられない |
| 決済が失敗した側の後始末 | `tests/payment.test.ts` | 鍵を入れたサーバーに向けて流す |
| 画面遷移・フォーム・一覧・レイアウト | `tests/e2e/*.e2e.ts` | 実際に描かないと分からない |

**計算を E2E で網羅しない**でください。E2E は「画面を通して正しい値が出る」を
1本だけにします。

**E2E のファイル名は `*.e2e.ts` です。名前に `spec` も `test` も入れないでください。**
入れると `npm test`（node:test）の収集に拾われて落ちます。逆に `.spec.ts` で作ると
Playwright の `testMatch` から外れて**黙って実行されない**ので、
`npm run check:scenarios` が見つけて落とします。
